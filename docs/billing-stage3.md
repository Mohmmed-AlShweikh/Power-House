# Stage 3 — billing settings and calculation core

Owner: More → إعدادات الفوترة. Price in shekels (converted once to integer agorot), arbitrary Arabic unit name (default وحدة), minimum consumption in units (3 decimals), cycle days 1–366, rounding threshold 1–99 agorot (default 50). An exact 20→30 reading example previews the chosen settings. This does not open a reading round.

The pure `calculateBill` is the single charge/rounding core. It calculates difference, applies a minimum before rounding, and captures the entire settings snapshot. Existing manual bill creation paths use it with previous=0 and current=entered consumption; stage 5 will supply actual previous/current meter readings. Stored snapshots and existing bills are not changed by later settings. The original full-invoice payment flow is unchanged. New zero-charge reading rounds are deferred to stage 5; the existing manual form still requires a positive invoice.

Canonical new data: `billingSettings/{generatorId}` (one document per generator), integer `priceAgorot`, integer `minimumUnitsMilli`, `cycleDays`, `roundingThresholdAgorot`, `unitName`, `generatorId`, `updatedBy`, server `updatedAt`. Bills add integer `amountAgorot` and frozen `billingSnapshot`; the old `amount` field mirrors rounded whole shekels for existing screens/payments. Raw numerator and denominator preserve sub-agora precision. Compatibility price controls preserve the other settings transactionally. Shared status/consumer tariff display uses this price; kWh labels in the touched billing/consumption views become the configured/snapshotted unit or default وحدة. The bill-count row is now labelled as a count.

Rules: verified active same-generator members may read these non-personal tariff settings; only an approved active owner can create/update validated settings. Super-admin has no new client override here. No delete permission. Other generators, pending accounts and consumers writing settings are denied. No existing authorization rule is relaxed for account/profile access. Bill-review snapshot fields cannot be edited by consumer payment submission or owner payment approval.

Cost: settings screen has one document listener; an active home/status screen adds one tariff listener (Firestore/Riverpod shares the provider within its scope). Each save writes one settings doc. Existing invoice creation additionally reads one settings doc, and writes the frozen fields in its existing bill write; no image blobs, Storage, Functions or server.

Manual: deploy this branch's rules as in `docs/manual-steps.md`; no new indexes, credentials, provider, migration or billing enrollment needed. Screenshots: `docs/screenshots-billing/settings_light.png`, `settings_dark.png` (widget goldens, not device photos).

Existing daily usage bars are still synthetic estimates from the previous implementation, not worker meter measurements; stage 5 must replace them with actual readings. Their unused compatibility cost estimate uses the pure rounding core without a per-cycle minimum. Weekly/monthly historical costs now sum stored bill amounts instead of recalculating old bills using today's price. These estimates are not new financial ledger entries.
