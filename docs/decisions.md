# Decisions

1. Branch from ad494a9 on `feature/spark-email-phase1` into `feature/free-tier-billing`, per the latest user update; not from the historical dual-login branch. Stage 2 already implemented: verify only, no auth rewrite.
2. Integer agorot for new money and integer thousandths for meter units. This permits 0.001-unit precision without binary floating-point; decimal inputs beyond precision are rejected, not silently rounded. Price is agorot per whole unit. Raw product retains integer numerator/denominator for sub-agora precision; apply minimum before whole-shekel rounding.
3. Stage 3 adds future-bill settings in a separate owner-only document. Existing manual bills and Phase-1 full-invoice payments remain unchanged until stage 5. No legacy-account migration.
4. Stage tags belong to this feature branch. Push only this branch and its explicitly named stage tags, never main or unrelated tags.
5. The existing manual invoice API now uses the same calculation core and stores `amountAgorot` plus a frozen `billingSnapshot`. Its old whole-shekel `amount` remains as a compatibility display field, always derived from the rounded result. Stale manually supplied amounts are rejected. This is not a legacy-account migration. Reading-difference rounds and partial payments remain stage 5.
6. Compatibility tariff controls write the canonical integer billing settings transactionally; the existing generator display API derives a decimal price only for display. Verified, approved same-generator consumers can read the non-personal billing settings (as they already read the tariff). Only the owner can write. All private reader access must be separately restricted in stage 4; it must not inherit consumer access.
7. A bill snapshot uses integer thousandths of an agora for raw products, with denominator 1000, so fractional units do not silently discard sub-agora precision before minimum/rounding. Price capped at 1,000,000 agorot and readings/minimum at 1,000,000,000 milliunits keep products below the exact integer range on web as well as Android. Threshold range is 1–99; exact whole shekels never receive an extra increment.

8. Stage 4: single-use 128-bit owner invitation, optional expiry, atomic user/staff/redemption. Workers register through the existing verified-email flow and choose the invitation link on onboarding; no second auth implementation. Revocation suspends the worker and disables staff access atomically. Workers use only sanitized assignment/current-round documents, never generator/private tariff documents. Public directory supplies tenant availability. Closed rounds are denied to workers. Existing bill/payment paths stay intact.

9. Stage 5 uses separate cycle invoices/payments to preserve Phase-1 manual invoices and their full-payment flow. New rounds support partial payments, integer balances, frozen tariffs and deterministic invoice ids. Opening is resumable (preparing), closing freezes worker writes and resumes per-subscriber transactions (up to 1000 subscribers per round). One pending declaration per invoice; reviews are idempotent. Manual subscribers can be linked once to a consumer UID and projections repaired. Offline worker writes use the native Firestore queue and metadata; no server promises.
10. To avoid silently changing subsequent readings, a closed reading can be corrected with reason only before a later round is opened. Corrections preserve before/after and actor/time; reverse payments first if a correction would create overpayment. Cascading later rounds/refunds are intentionally not automatic. All new invoices remain unpublished until stage 6. Existing daily usage estimates are not relabelled as real readings; the new round/statement screens are the authoritative meter ledger.
11. Priority updated to 4 → 5 → 7 → 6 → 8. Finance includes both Phase-1 manual invoices and cycle invoices. Summary dates distinguish period cash receipts from receivables for period invoices. Transactional read/modify/write of the affected summaries is used for exact counters across SDKs. Repair uses a locked generation swap, retaining prior generations and expense before/after records; no destructive cleanup. Cash excludes opening balances and is not a bank balance.
